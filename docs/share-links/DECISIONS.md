# Share links: decision log

Why each choice was made, in the words of the conversation that produced it (2026-10-19). The plan that follows from these is in [PLAN.md](PLAN.md); the mockups are in [mockups/](mockups/). Anyone (including a future session of the assistant) picking this up should read this file first, then the plan.

**Who decided what.** "Owner" is the gallery's owner (the person who asked for the feature). "Assistant" proposed; the owner approved, changed or rejected. Where the owner changed course, the note says so.

## 2.3.1 additions (owner's requests, 2026-10-22)
- **A scope that grants nothing: "Just the public gallery".** The owner couldn't make a logged link without also giving something private, and wanted to learn who opens an address they post. A fourth scope; downloads and *show only* are forced off for it (they would be meaningless, or would show the person nothing at all).
- **The public address's log is a record in the links file** (fixed id `ffffffffff`, `kind: public`, no address) so every log page, the IP list and the CSVs work unchanged; nothing can look it up by address or cookie, and every action except trim and delete refuses it. **The switch lives in Settings** (owner: switches live in Settings, results in the Shares tab). **A visit** is a visitor arriving or back after 30 minutes, since there is no button to press. Logged only through the page's own script (so most bots drop out) and never for the owner, private-view visitors, link holders or preview bots. **Kept 30 days by default**, trimmed once a day by the next visitor's arrival, because it stores IP addresses.
- **One set of tabs for a link and for an address** (owner, reading two screenshots: the IP address button and the "21 views ›" button led to two different pages for the same person, one with Folders / Media / Timeline, one with Visitors / Folders / Photos): a link is Visitors / Folders / Media / Timeline, an address is Folders / Media / Timeline, the same tables and menus, and pressing an address changes the scope to it. Media was "Photos" and holds videos too. The Folders numbers are buttons to Media; "Opens" is the folder page, not photos opened (the old "Views" column mixed them).
- **The Media filters are three menus on one line that narrow the same media together** (owner: "all ips, all folders, most viewed, or 1 ip, 1 folder, private"): addresses and folders take any number of ticks, the third is one choice (*Most viewed, Most recent, Photos, Videos, Private, Opened, Downloaded*; the assistant first read it as a sort plus filters and was corrected). The earlier "Seen only / Played" choices went. *Saved* became *Downloaded* everywhere in the log so the filter and the labels agree.
- **The opening page shows the whole photo, not a banner** (owner, comparing it with the same photo's folder card: "asinine"): I had forced the picture into the message preview's wide 1200 x 630 shape and kept the middle, so a portrait lost its head. Now it keeps its own proportions, full width up to 60% of the screen's height. The owner chose this over using the card's square. The message preview's own picture is left as the whole photo; the chat app's crop is not ours to control, and a fitted 1200 x 630 card was offered and not taken up.
- **The preview photo is shown before it is made, and can be chosen** (called the *cover* photo at first; the owner: "it should be called a preview photo", since a folder has a cover and the link's picture is what shows in the message preview) (owner: "why not just show the user what you're going to use right away, allowing them to accept it or choose their own?"): a link gets a small random number when it is made, the automatic pick is worked out from it, and the form asks the server for the same answer. *Choose…* lists public photos only; the choice is checked when it is saved and every time it is used (a private or deleted photo falls back to the automatic pick), so editing a request by hand can't make a private photo a cover. No "Another one" button: choosing covers it.
- **"The gallery's cover" was never a feature** (owner's correction): the star on a photo sets that folder's cover, and for the top level that is just the top-level folder's cover, which the preview happens to use first. It only exists when photos sit directly at the top level. The wording that said otherwise is gone.
- **Menus apply as you tick** (owner: "it should respond instantly"): my first version applied a many-tick menu when it closed so the list wouldn't vanish under the pointer; the page now re-opens the menu where it was after each answer. A tick on a folder includes the folders inside it (a tree), and the Folders tab's numbers, which count a folder's own files, lead to "this folder only".
- **A link's settings are folded under "Settings", closed** (owner: it opens a link to look at its activity, not to read ten lines it knows). Edit… lives inside.

## The idea

The owner currently gives people a *private-view password*. They want to stop handing out a password and instead hand out **temporary links**: `https://example.com/trip/<random>` that automatically sign the person in as a "private viewer", usable only N times and/or until a time. The password option stays in the project for admins who prefer it; **nothing in the share-link screens should mention the password**.

## Where it lives

- **A new "Share links" tab in the admin**, next to Private, not a Site-settings section. *Why:* Settings holds on/off options saved to `.gallery-config.php`; links are records that change constantly (use counts, pause, revoke, logs).
- **Settings gets only**: *Allow share links* (off by default, like every opt-in), the short-address check, the heads-up default (off), where visitors' IP addresses come from, and a Cloudflare-caching note.
- Storage: `.gallery-links.php` beside `index.php` (the same guarded-PHP-JSON pattern as `.gallery-items.php`), plus one log file per link. They are matched by the existing `/\.gallery-` web-server rule and need adding to the README's backup list.

## The link and the opening page

- **Address `/trip/<16 letters and digits>`** (the owner's gallery is at `/trip/`). It needs a web-server rewrite, exactly like the existing tidy folder-link rule; the rule shown in the admin is **written for the user's own install** (derived the same way as the other rules), with an nginx and an Apache version, and a live probe. Without the rule, `?link=<token>` works with no server setup.
- **Token is stored readable**, not hashed, so the owner can copy a link again later (they re-send links by message). The file is guarded and not served.
- **"Open the gallery" is a button; pressing it is the "use".** Chat apps fetch links to build previews; counting the page fetch would burn a one-time link before the person saw it.
- **A "use" is a new browser**, not a page view. Once someone is in, they can keep looking until the link ends. *Added after the owner pointed out in-app browsers:* a link tapped inside Instagram/Facebook opens in that app's browser and the person then taps "Open in Safari"; a second open from the **same IP within ~15 minutes is not counted**, so a *Once* link survives that hand-off.
- **Invalid / expired / used-up / revoked / paused / mistyped links all show the same page.** Owner: it should have **no "Go to the gallery" button and no "public photos are still there" line**, no "it may have ended or been used up", and no domain footer. The point is for the person to tell whoever sent it, not to go poking around. Text: "This link isn't valid" / "Please let the person who sent it to you know."
- **The opening page has no domain footer.**
- **Optional personal note** per link, shown on the opening page ("Hi Carol, here are the Rome photos…").
- **Title on the opening page and in message previews is configurable per link:** the gallery's title (default), a neutral "A shared gallery", or custom text. The icon is always the gallery's. *Owner:* fine for now, but make it configurable "in case there comes a time when it's not ok for a given share link". Message previews never show a folder name. *(Changed in 2.3.1, the owner's request: a link can show a cover photo, from the public folders only. The box is on by default when the title is the gallery's own and off with a neutral or custom title, and can be changed per link. It is worked out as a signed-out visitor sees the gallery and is stable per link; the opening page shows it too.)*
- Opening page headers: `Cache-Control: no-store`, `X-Robots-Tag: noindex`, `Referrer-Policy: no-referrer`.
- After pressing the button the browser is redirected to a clean address (the token is not left in the address bar or history).

## Access, status and lifetime

- **The cookie is checked against the link's record on every request.** Revoking, pausing or expiring cuts off people already in. It is bound to the token, so *Replace address* also signs everyone out.
- **Link holders are never admins.** No pencils, locks, Private tab or sign-in lock in the icon strip. *Admin implies private view, never the reverse.*
- If the owner (signed in as admin) opens a link, the admin session wins and nothing is counted or logged.
- **Statuses:** Active, Paused (reversible, "Resume"), Used up, Expired (**"Extend…"** is offered), Revoked (final; stays listed with its log).
- **Starts-on date**: the owner said it isn't super useful but fine to add, default *Immediately*.
- **Opens**: Once / 5 / 10 / Unlimited / other. **Ends**: 1 day / 1 week / 30 days / a picked date / never. Times are entered and shown in the owner's browser time zone.
- **Heads-up header** (the visitor sees a thin line at the top): *can be turned on/off, including per link* because the owner isn't sure they like it. Site default off; per link: use the site setting / On / Off. **Wording (owner's):** "The link being used to access this media expires on <date>." Amber in the last day; dismissable; not shown when the link has no end date.
- **Replace address**: new token, same name, settings and log; the old address stops working at once and, if pressed, is logged as a blocked try.
- **Preview as this link** (opens in a new tab): shows exactly what the link shows; counts nothing and logs nothing. Needed to check a folder-limited link before sending it. **How it really works (changed while building it):** the first plan said the new tab would have "its own sign-in" so the owner stayed signed in as themselves in the first tab, but cookies are shared by every tab of a browser, so that can't be done. A signed preview cookie (4 hours, or until *Exit preview*) therefore makes the whole browser see the link's view on gallery and media pages (never on `?admin`, and a picture an admin page asks for is still the owner's, so the admin's thumbnails keep working). Every gallery page in that browser shows the purple strip with *Exit preview*, and the Shares tab shows a note with *End preview*, so it can't be mistaken for the owner's view. Rejected: asking the owner to use a private window instead (more steps, and no strip or list of what's included).
- **A new-activity badge** on the Shares tab/row (no email; the gallery has no mail).
- **Not included:** emailing the owner on first open.

## What a link can see

Three scopes, all in the first version (owner: "option for everything and specific folders… in the first version"; photo scope added later in the conversation):
1. **Everything private** (including things added later).
2. **Only some folders** (each includes everything inside it). The link holder is never told other private folders exist: no counts, no lock icons, no hints.
3. **Only some photos** (from the viewer's link button, or Select mode's *Share…*). They see those, and whatever is public (in a public folder, closing the viewer shows its public photos too). Added 2026-10-20: a link can **show only its own** things (`only` on the link; on by default from one photo or Select, off for folders), which takes the public rest of the gallery out of the pages the person sees: a tidy view, not a lock, since a public photo can still be opened by its address.

**Folders are remembered by a hidden id stamped into the folder's own `.gallery-items.php`** (the owner chose this over path-matching: "you don't rename something to hide it normally"). The id travels with a rename or move; a deleted folder is "missing"; a **same-name newcomer is not covered**; a copied folder (duplicate id) is ambiguous so it fails closed with a warning; if the folder isn't writable, creating a link for it is refused (no silent fallback to paths). Each link remembers the folder's last path and checks that first, rescanning only if the id has moved. Photos are remembered as folder id + filename; a renamed/deleted photo is "missing" too. A missing item fails closed and the link row shows "Folder missing" with *Pick it again…* / *Remove it from this link*.

## What a link can do

- **Download originals** and **ZIP of a folder**, each: Off / everywhere they can see / only in chosen folders (when the scope is some folders the wording is "In all chosen folders / Only in some of them"). Public photos follow the gallery's own download setting.
- **Photo locations.** The assistant first said visitors "never" get locations; the owner corrected it: *visitors do get locations when "show locations publicly" is on for the folder.* The real model: a link holder by default sees **only the locations visitors already see** ("as the public sees them"); the alternative is "all saved locations". Hidden locations are **scrubbed from originals and from the ZIP** for link holders (the ZIP today ships files "exactly as on the server, locations included", so it needs the same scrubbing single downloads already have).

## The link button on private media

- The viewer's copy-link / permalink button on a **private** photo (and on a private folder's card):
  - **for the owner**: opens a small popup, "This photo is private", with **one row of two buttons**: *Share just this photo…* and *Copy link* (the owner asked for the buttons on a single line);
  - **for everyone else** (link holders, private-view visitors): **the button is hidden**, because a plain link to a private item is useless to anyone without access.
- Public items keep the button for everyone.
- Why a private link is useless: `?photo=<private>` for a viewer without access just loads the plain gallery with no photo and no preview picture, and `?img=` answers 404; the copied address never contains the share token.
- A photo that follows a private folder counts as private; a photo explicitly made public inside one counts as public.

## Sharing aids

- **Share this folder…** button on a private folder's page and on the Private tab's rows: opens a short form already set to that folder (name, folders, opens, ends, *More options…*). *Why:* otherwise the owner has to go to the tab and find the folder in a list.
- **Share…** in Select mode for a few photos.
- **Copy**, **Share…** (the phone's own share sheet) and a **QR code** with the **gallery's own icon in the middle** (error correction H so the icon is safe). The QR has a **large preview** (a white full-screen version for showing someone across a table), **Copy image** and **Save image**.
- **Export log as CSV** (visitors / what they looked at / everything in order), per link and per IP.

## The log

The owner wants to see "what folders and exactly which media any given IP looks at", across all links, and never to lose a log when a link ends: **"Revoked/expired != deleted. Logs are deleted only when the link is deleted."** The delete confirmation counts what will be lost.

- **Four levels, because thumbnails are sharp enough to count as seeing a photo** (owner: "if we only show the media an IP looked at, defined as opening it in the lightbox, we're not being truthful"):
  **Seen** (on their screen, even as a thumbnail) · **Opened** (shown large in the viewer; **Played** for a video) · **Saved** (the original downloaded).
- **"Seen" is reported by the visitor's browser** (IntersectionObserver, sent in small batches), not counted from image requests: browsers keep public images for a year, and a CDN may keep copies, so image requests don't say what was on screen. The server also notes deliveries of *private* items as a backup so an ad-blocker can't hide the sensitive ones.
- **Cloudflare was checked on the live site** (2026-10-19): pages and `?img=` images return `cf-cache-status: DYNAMIC`; nothing is cached at the edge today (Caching Level Standard, Browser Cache TTL 4 hours; the owner believed there was a Cache Everything rule, but none matches these URLs).
- Per link, per IP: browser, country, opens, and per item first/last seen and counts. A timeline of the **latest 300 events per link**; older events fold into the counts so nothing is lost. Latest **200 visitors per link** ("+N earlier").
- Views: **the IP's page** (Folders / Media / Timeline tabs; filenames are shown because only the owner sees it), an **all-IPs list across links** ("an address on two links is worth a look"), and **blocked tries** with IP (a forwarded link being tried by someone else).
- **An IP is not a person**; the screens say so.
- Link holders' views are kept out of the public view counts.

### IP addresses behind Cloudflare
`REMOTE_ADDR` is Cloudflare's address. A setting "Where visitors' IP addresses come from" (Directly / Cloudflare / another proxy). With Cloudflare, `CF-Connecting-IP` is trusted **only when `REMOTE_ADDR` is in Cloudflare's published ranges** (built in, editable). This also fixes the existing sign-in throttle, which currently sees only Cloudflare addresses.

## A closed gallery and addresses of your own (2.3.1)
- **A closed gallery answers as an invalid link, not a "private" page** (owner, 2026-10-23: "something more generic like \"This link is not valid. Please contact the person who gave it to you.\""). Same page, same 404, same headers as a mistyped link, so a stranger can't tell a closed gallery from a bad address, and it never counts as a failed guess. Open to everyone when closed: a link's own address and opening page, the sign-in, and the `share`-size picture of a photo that a live link uses as its preview (chat apps fetch it with no cookie). A folder typed without its slash is not sent on for a stranger.
- **The setting needs a way in** (owner: "reasonable, no? otherwise no one could get in at all"): refused while share links are off or no admin password is set, and share links can't be switched off while it is on. The private-view password is not required (the owner has turned theirs off in favour of share links).
- **`/admin` goes to the combined sign-in** (`?reveal`: the admin password or the private-view password), not an admin-only page, so someone who uses the private-view password can use it too. `/admin` is easier to remember than `/?admin`. It rides on the same server rule as links (a reserved word), so no second rule; a real folder named `admin` is not shadowed (the folder wins for `/admin/`).
- **A link's address can be fully custom**, with the random token as the default; a **Use the name** button makes one from the link's name in one press. Rules: 4 to 40 letters, digits and hyphens; refused for a top-level folder or file (any case), a reserved word, another link's current or old address. A custom name is stored in lower case and answers in any case.
- **A link beats a folder of the same name, by the shape of the rule, not by detection.** The first draft said no rewrite rule could do that (true of the old Apache rule, whose `!-d` lets the folder win; the nginx rule has no such check). The new rule has neither check and matches one word without a dot or closing slash, so `/dir/name` always reaches the gallery: the gallery opens the link of that name, else (a real folder) sends the visitor on to `/dir/name/` as the server would have, else a plain invalid page. A folder's own address (with the slash) never goes to a link. The Shares tab still says when a folder has a link's name. The price: the old 16-character rule must be replaced by the new one, and every one-word path now passes through the script.
- **Guessing a name is held back like guessing a token** (five wrong tries, then a short lockout). The form warns that a short name can be guessed and the README says to keep random addresses for anything sensitive.
- **An old address can be kept working (2.3.2, owner's idea: turning a random address into a name without breaking what was already sent).** An opt-in tick box in Edit, shown only while an address that exists is being changed, off by default (a changed address normally means "stop the old one"). The kept address is a *redirect* (302, `no-store`, never 301: a browser caches a 301 and it would outlive the Remove) to the present address in the same form the person used (short or `?link=`), so a copied address bar holds the new one. Only for an *active* link: a paused/expired/revoked link answers the kept address with the invalid page and gives the present address away to no one. It is stored on the link (`aliases`: name, custom, added, hits, last), at most nine, counted at each use, listed in Settings as *Also works at* with Remove. Remove and *Replace address…* move the names to the replaced list (so they stay reserved and are noted as "replaced" in the log); Replace is the leak button, so it takes the kept ones with it. Changing back to a name the link keeps makes it the address again. The signed-in cookie is tied to the present address, so a change still signs people out; coming in by the kept address just shows the opening page again. The server rule is unchanged (it already sends every one-word path to the script).
- **An old address is working, paused or killed (2.3.2, owner's design: "Kill / Pause / Resume"; kill allows the name to be used elsewhere).** Working = `aliases`; paused = the old `oldTokens` list (shown now as *Paused addresses*, reserved to the link, never trimmed), with the address's visits and last use kept in `aliasStats` so Resume gives them back; killed = removed from every list so the name is free, with a one-line summary kept in `killed` (short label only: never the address, so it can't be revived; cleared with one button). Pause and Resume ask nothing (reversible); Kill asks and, for a custom name, warns that anyone holding the old address would land on whatever uses the name next. Tries on a paused address are counted in the log (`tried`, per visitor and address, next to `via`). A killed address is an unknown address: it counts toward the failed-guess lockout, a paused one doesn't. The *keep* box is ticked each time it appears (owner: the address that was sent should keep working); *Replace address…* stays the hard cut-off and pauses (keeps reserved) rather than frees. This supersedes the next point's wording ("Bring back" is now Resume).
- **Replaced addresses can be brought back (2.3.2).** The replaced list was never shown; now Settings lists it by first and last four characters, with Bring back (replaced list → kept list, the limit of nine applies). A custom name is checked again as when it was chosen (a folder may have taken it since); an address another link holds is refused. The list is never trimmed (it used to keep the last five): forgetting a replaced address would free its name for another link; it is a few short strings per link, so there is no cost to keeping them all. The kept list is capped at nine (owner's choice: ten ways in in all, counting the present address). Whether an old name is custom is told by its shape (a random code is exactly 16 letters and digits with a capital among them), so a replaced list entry needs no extra field.
- **"Came in on" is recorded when a kept address redirects (2.3.2).** The visitor then presses *Open the gallery* on the present address, so the open itself can't say which address they typed; the redirect writes `via[visitor] = {ip, addresses: counts, last}` in the link's log (capped like the visitors, trimmed with the log). Shown only when the link has (or had) a kept address; a visitor with no note is shown the present address if first seen after the link got its second address, else a dash (we never knew). Format `via: name` or `via: k7Q2…Tb4e`. Phone: a line under the IP (the table already scrolls sideways there); wide: a column. Not a tab: with one entry per visitor and a handful of addresses a tab would be almost empty.
- **The Replace address dialog is Cancel, Random, Custom…** (owner's wording, so the three fit on one line on a phone); the row's action keeps the name *Replace address…*. *Random* is what the button always did (a new random address, the old one a replaced address); *Custom…* hands over to Edit with the Address focused, so a custom name is only ever chosen in one place. For a custom link the text says Random drops the name.
- **The Health check's tidy-folder probe treats the invalid-link page as "works".** It asks as a visitor who isn't signed in, which a closed gallery turns away; only the gallery sends that page (with its marker header), so it proves the rule reaches the gallery.
- **Not decided: a name with the owner's own words** (more than 40 characters, spaces) is not allowed; a slug is.

"Preview as", "Replace address", "Share this folder…", CSV export, message previews that don't leak, in-app-browser re-open grace, owner opening own link, view counts excluded, "folder missing" handling, no owner tools for link holders, batching the log writes, times in the owner's zone, backups/docs/tests housekeeping.

- **The new-link form, the links list, downloads and the Settings page were reworked together (2.4.0, the owner, after using it: "it's too excessive").** The decisions: (1) *Opens* default to Unlimited and *Stops working* to Never, in both forms; the rest of the defaults are unchanged. (2) The form shows the name, the address and one sentence about what the link will do, then four folded rows; what is not the default is darker and bolder (in the sentence, and in a link's paragraph on the list), and a row says *Changed*. The Settings page does **not** mark changed settings (the owner did not want it). (3) The address is made from the name by default only when the link shows nothing private (a guessable address on a link to private photos is the risk); a private link starts random with a note; a taken name gets a number. The old hyphenated "Use the name" is gone (no hyphen). Existing links keep their stored off / all / some, which now mean Off / Everything / Only some folders (owner's decision: "old links move to the new meaning"). (5) **Photo locations** are *Shown only* / *All*: the first follows the folder and photo location switches (never "the public's"), and the folder switch says "to visitors". (6) A link's address box is gone (a hidden field feeds Copy link, Share… and QR); Copy appears in the share kit only when the row's own button is not Copy link. (7) The QR code opens large at once. (8) Settings: every group closed, two groups split, one renamed, sign-in and passwords merged, Prepare media under Thumbnails and drawn only while thumbnails are on.
- **"Files this gallery has made" (list, ZIP, delete), and why the delete is built the way it is (2.4.0, the owner: "you could ruin someone's very special memories").** One plan builder (`owned_plan`) feeds the list, the ZIP and the delete, so the delete can only touch what was shown. Exact names plus two strict patterns, never a wildcard; direct children of a folder the gallery scanned; a regular file, never a link; data files must start with the gallery's own guard line (a hand-made lookalike without it is "left alone"); one `unlink` at a time; `rmdir` only on an emptied `.gallery-cache`; one bad entry means nothing at all is deleted; the settings file goes last; the plan's fingerprint is sent with the last button and rechecked. The ZIP snapshots each data file under a shared lock (a half-written copy is no copy), is laid out as on disk with a README, needs the password again, is no-store, and leaves thumbnails out unless ticked. Not built: select-photos for downloads; restore from the page (unzip by hand); the delete does not remove `index.php` or `.gallery-setup`. The tests use decoys and a checksum of everything not ours before and after; `tests/tools/skeleton` makes a read-only skeleton of a real gallery (mapped folders included) that `build_fixture.py` turns into a stand-in to run the same delete and an exact round trip on. **The delete is not called release-safe until that has been run on the owner's skeleton.**

## Out of scope (for now)
Email/push notifications; a per-photo "what did they look at" *history beyond the 300-event timeline*; hashing tokens.

## Risks to keep in front of us
- **Visibility is checked in many places** (≈21 `is_revealed()` and 13 `file_is_hidden()` call sites). A folder- or photo-limited viewer must be right in every one: thumbnails, originals, video, map, search, counts, ZIP, sorting. Plan: a viewer-scope abstraction used by all of them, a leak test per route, and the fuzz suite run as that viewer.
- **"Once" must really be once** under simultaneous requests (lock the count).
- **Real iPhone/Safari behaviour** (Share sheet, copying the QR image, the full-screen QR, in-app browser hand-off) cannot be tested here; the owner will check on a real phone against their working trip gallery.
- **The admin stays signed in with a server-side token, not a longer session or a signed cookie (2.4.0, owner: "I'm constantly logging in", especially on a Home Screen app).** The cause was a session cookie with no expiry (iOS drops it when the app closes) plus a four-hour server life. Three ways were weighed: (1) a persistent PHP session cookie: depends on the host keeping session files for weeks, which Debian's cleaner and a container restart don't; (2) a signed cookie holding only an expiry: stateless, but *Log out* could not end a copy of it; (3) a random token whose hash the server keeps in `.gallery-stay.php` (expiry, the admin-password mark, last seen), chosen: logout deletes that one device's token, a password change ends them all (the mark is the same one the session uses), twenty kept at most. Renewal is at most once a day so the file is not rewritten on every request. No tick box on the sign-in page (it is bare on purpose): a setting, 30 days, 0 = off. A token never skips the CSRF token, and a script sending a Basic header is left alone (it neither gets nor uses one). Restoring a session makes a new CSRF token, so a page opened before asks to be reloaded.
- **Changed after the owner's objections (2.4.0, 2026-10-30).** (1) *Prepare media* appears the moment *Thumbnails* is turned on (the switch saves at once, then the page asks for the panel and sets it up), not after a reload. (2) The ZIP of the gallery's own files has no size cap: the earlier 64 MB limit existed only because data files were read into memory to get a consistent snapshot; they are now copied under a shared lock to temporary files and streamed like the ZIP of photos. (3) After a delete the gallery is plain and public, and `?admin` shows nothing until the person adds `.gallery-setup`; the delete does not create that file itself, because an open setup window lets whoever arrives first choose the admin password.
