## Fixed (2026-10-23, 2.3.1-dev: closed gallery, /admin, custom addresses)
- [x] **Close the public gallery (new setting)** (owner, 2026-10-23). Site settings, in the Share links section: "Close the public gallery". When on, only these get in: the owner, a private-view sign-in, and someone holding a share link's cookie. Everyone else gets **the same page as an invalid link** ("This link is not valid. Please contact the person who gave it to you."), not a separate "private" page, so a closed gallery can't be told from a bad link; noindex, no title, no photos, no lock icon, and it never counts as a failed guess. Stays reachable when closed: `/TOKEN` and `?link=` (and the link's opening page), the sign-in pages, and the one `share`-size picture of a photo that a live link uses as its preview (chat apps and the opening page fetch it with no cookie). **Refused** while share links are off, or no admin password is set (nobody could get in); and turning share links off while closed is refused too, with a message to open the gallery first. A pretty **`/admin`** (also `/admin/`) goes to the combined sign-in (admin or private-view password); `?admin` keeps working without a rewrite; the rewrite rule goes beside the tidy share address's in Settings and the Health check, ahead of the folder rule; a real folder named `admin` would shadow it, so the Health check warns. Share tab: the "Public address" card says "Closed: no one can open the gallery without a link"; "Log visitors to the public address" gets a note that nothing is logged while closed (the old log stays). Caveat shown with the setting: a bare file address still works unless the server rule that answers 403 is in place (the same limit private folders have). Tests: closed and a stranger gets the invalid page (and the same status as a bad link); owner, private-view and link holder get in; the link entry, its preview picture and `/admin` stay open; refused with share links off or no admin password; `/admin` reaches the sign-in; the cookie of a revoked link gets the invalid page.
- [x] **Custom share link names (owner said yes 2026-10-23; the owner's server is nginx with `gallery.inc`; the new rule REPLACES the existing 16-character one: `location ~ "^/trip/([A-Za-z0-9][A-Za-z0-9-]{2,38}[A-Za-z0-9])$" { rewrite "^/trip/([A-Za-z0-9][A-Za-z0-9-]{2,38}[A-Za-z0-9])$" /trip/index.php?link=$1 last; }`, pasted only AFTER the new index.php is in place; the Settings and Health check snippets are generated with this pattern for both servers; a name-shaped miss such as `/trip/rome` then answers the invalid-link page instead of falling through to the site index)**: a link may have a fully custom address instead of its random token (the random token stays the default). A **"Use a name from the label"** button beside the field turns "Who is this for" into a name in one press (lowercase, accents removed, anything else becomes a hyphen: "Dyllen and Brenden" becomes `dyllen-and-brenden`); the result stays editable and is checked like a typed one. Rules at save: 4 to 40 characters, a-z 0-9 and hyphen, not starting or ending with a hyphen; refused (with the reason named) when it matches any top-level folder or file of the gallery (compared without regard to case), a reserved word (`admin`, `index`, `reveal`, ...), another link's current or old address; a short or plain-word name shows a warning that it can be guessed (the failed-guess throttle is then the only defence). Later clashes (a folder added by FTP after the name was chosen): **prevented by the rule's shape, not only detected** (corrected 2026-10-23: the first draft said a link can never beat a real folder; that is only true of the current Apache rule, whose `!-d` check lets the folder win; the nginx rule has no such check). The new rule has no `!-f`/`!-d` check and matches any one-segment name without a dot and without a trailing slash, so `/dir/NAME` always reaches the script; the script opens the link when NAME is a link, and otherwise, if NAME is a real folder, redirects to `/dir/NAME/` (what the server would have done), else 404. A folder's own address (`/dir/NAME/`, trailing slash) is never touched, so link and folder can share a name. Detection stays as a safety net (Share tab and Health check flag a rule that is old or not installed, with `?link=NAME` shown beside the address). Apache runs `mod_rewrite` before `mod_dir`'s slash redirect, so the folder should not win; the owner checks that once on their server. The rewrite becomes looser than the exact-length token; an unknown name-shaped path without a dot counts as a failed guess, anything with a dot (a missing `favicon.ico`) is a plain 404 and not counted. Changing the name makes the old one a "replaced" address (as a new random token does now). Tests: name from label; every refusal; shadow detection; `?link=NAME` works; replaced name; throttle counts a name-shaped miss and not `favicon.ico`. Cannot be tested here against Apache or nginx (only `php -S`): the owner checks the rewrite on their server (PHONE-CHECKLIST).

Owner to verify on the live server (see PHONE-CHECKLIST, "Closing the gallery, your own addresses, /admin"): replace the nginx rule with the new one only after the new `index.php` is in place.
